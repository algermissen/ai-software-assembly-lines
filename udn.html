1. Unified Development Namespace (UDN) — Detailed Implementation

← Index

Architecture Overview

Event-driven semantic hierarchy acting as the real-time single source of truth. All producers (GitHub, CI, agents, observability, humans) publish CloudEvents or structured payloads to hierarchical topics. Consumers (agents, MES, dashboards, SPC) subscribe selectively. No point-to-point integrations.

[Producers] → [Event Bus: NATS JetStream / EMQX MQTT / Kafka]
   Topics: org/{org}/team/{team}/repo/{repo}/event/{type}/...
   → [Consumers: Agents, Orchestrators, Metrics, Dashboards]

Hierarchy inspired by ISA-95: Enterprise → Site/Team → Area/Repo → Line/PR or Issue → Cell/Step.

Technology Choices (2026 practical)

  • Event Bus: NATS JetStream (low latency, simple ops) or EMQX MQTT (UNS familiarity, retained messages for current state). Kafka for high-volume replay needs. Bridge GitHub/Linear/Jira webhooks via lightweight ingest (e.g., custom Go service or Siphon-like).
  • Payloads: CloudEvents 1.0 + custom data schema (JSON or Avro with schema registry). Include correlation_id, work_order_id, agent_session_id, prompt_hash, model_version, confidence.
  • Observability: OpenTelemetry (gen_ai.* semantic conventions) for traces; publish spans as events or link via trace_id in namespace.
  • Storage/History: Event log retention in JetStream/Kafka; materialize current state to ClickHouse or Postgres for queries; optional digital twin in graph DB.
  • Security: Topic ACLs, mTLS, short-lived credentials. Agents authenticate as principals.

Defined Datapoints & Metrics

  • Event fields: timestamp, topic, event_type (pr.opened, agent.step.completed, test.failed, deploy.succeeded), payload (diff_size, tokens_used, test_results, quality_score), lineage (parent_event_ids, agent_id, human_id).
  • Namespace metrics: publish rate, consumer lag, topic depth, schema compliance rate, subscription coverage.
  • Derived: mean time to context (how fast agents get relevant events), event completeness score.

Development / Operations Process Flow

  1. Human or product system creates validated intent (ticket in Linear/Jira) → publishes intent.created to namespace.
  2. Orchestrator/MES subscribes, creates production order, publishes order.scheduled.
  3. Agent stations subscribe to relevant topics (e.g., .../order/{id}/ready_for_implement), pull work, publish progress events continuously (agent.tool_called, code.committed).
  4. Quality gates (CI, other agents) subscribe to code.proposed, run checks, publish pass/fail with details.
  5. On abnormality, Jidoka station publishes andon.triggered; flow pauses until resolution.
  6. Successful deploy publishes deploy.completed; runtime telemetry (OpenTelemetry) flows back into namespace under runtime/... topics for closed-loop feedback.
  7. All history retained for genealogy, Kaizen analysis, and SPC.

Agents receive fresh, contextualized state without polling. Adding a new agent or tool = one subscription. Continuous stream is observable and constrained by topic structure and event contracts.

Adversarial Assessment (updated)

Pros remain strong for scale and coordination. Implementation risk is mainly ontology design and ensuring producers emit rich events. Start with GitHub + agent events on NATS; expand. Governance via schema registry and ACLs is mandatory.
